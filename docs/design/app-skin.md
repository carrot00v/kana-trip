## 1. 스킨의 정의

스킨은 앱이 입는 "여행지의 분위기"다. 기리의 차림(머리·속재료·밥)은 기리 몸에만 걸리고, 스킨은 기리가 서 있는 앱 화면 전체에 걸린다. 한 번에 하나만 쓴다. 고르지 않은 상태가 기본 스킨(지금 앱 모습)이다.

### 1.1 스킨이 바꾸는 것

| 자리 | 바뀌는 것 | 토큰 (2번) | 비고 |
|---|---|---|---|
| 화면 바탕 | 바탕색 | `AppBackground`, `AppBackgroundQuiet` | 약 단계 화면은 `Quiet` |
| 바탕 무늬 | 이어 붙는 무늬 타일 하나, 색, 진하기 | `pattern`, `PatternInk`, `patternOpacity` | 강·중 화면만(4.1) |
| 강조색 | 주 버튼 바탕, 보조 버튼(`.bordered`) 글자·옅은 바탕, 글자 버튼, 진행 막대, 할 차례 세션 번호 원, 홈 메뉴 아이콘, K의 고른 탭·쓰는 중 외곽선·체크 배지·미리 보는 중 점선 | `AccentColor`, `AccentForeground` | 앱 루트의 `.tint`가 이 값을 따른다 |
| 홈 지도 | 바탕(위 두 줄과 같음), 앞길 선, 잠긴 칸 테 | `AppBackground` + 무늬, `PathEdge` | 4.2. 지도 영역 안에서 스킨이 바꾸는 것은 이 둘뿐 |
| K 미리보기 | 기리 뒤 그림 | `giriBackdrop` | 배경 아이템 그림(`Item-{id}`) 그대로. 기리 뒤에 그림을 까는 곳은 K 미리보기 한 곳뿐이다(reward-flow.md 7번 그대로) |
| 내비게이션 바 | 바 뒤에 비치는 바탕 | (바탕을 따름) | 바는 투명. 제목 색(`Ink`)은 고정 |

탭 바는 앱에 없다. 뒤에 생기면 바탕은 `AppBackground`, 고른 탭 색은 `AccentColor`를 따른다.

### 1.2 바꾸지 않는 것

| 자리 | 고정하는 토큰·값 | 이유 |
|---|---|---|
| 글자, 제목, 판정 문구, 획 데이터 글자, 캔버스의 완성된 획·가이드 획·쓰는 중인 선 | `Ink`, `InkSecondary` | 획 모양과 대비가 학습 내용이다. 쓰기 화면의 선 색이 스킨마다 다르면 "맞아서 진해졌다"는 감각이 흔들린다 |
| 카드·캔버스·선택지·말풍선·목록 행·시트 안 카드 바탕 | `CardBackground` | "종이"는 늘 같은 종이다. 캔버스 바탕이 같으면 가이드 획(`Ink` 0.22)의 보이는 정도도 같다 |
| 카드·선택지 외곽선 | `Outline` 2pt | |
| 맞음·틀림 | `Correct`, `Wrong`, 아이콘 모양, 문구, 햅틱 | 화면에서 초록·빨강의 뜻이 바뀌면 안 된다 |
| 힌트 | `Highlight`, `HighlightStrong`, `OnHighlight` | 시작점 번호 원, 고리 점선, 엔 아이콘, 지도 지금 칸 발판 |
| L1의 "지금 글자" | 글자 색과 밑줄을 `AccentColor` → **`Ink`** 로 바꿔 고정. 형광펜 바탕(`Highlight` 0.45)은 그대로 | 강조색이 스킨을 따라가면 학습 글자의 색이 스킨마다 달라진다. 기본 스킨에서는 두 값이 같아 모습이 바뀌지 않는다 |
| 홈 지도의 지난 길·완료 칸 테·자물쇠·체크·발판·건물·스티커 | `InkSecondary`, `Correct`, `Highlight`, 그림 그대로 | home-map.md 7.3 |
| 글꼴, 텍스트 스타일, 가나 크기, Dynamic Type | visual-rules.md 2번 | |
| 배치, 간격, 버튼 크기, 모서리 반지름 | visual-rules.md 3·4번 | 스킨은 색과 그림만 바꾼다. 화면 구조는 하나다 |
| 기리 그림, 아이템 그림, 단어 그림, 장면 그림 | 그림 그대로 | 다크용 그림을 따로 두지 않는 방침 그대로 |
| 시스템 확인 창(`confirmationDialog`)의 버튼 색 | 에셋 카탈로그의 `AccentColor`(기본 스킨 값) | 시스템 창은 앱 환경값을 다 따르지 않는다. 억지로 맞추지 않는다 |
| 앱 아이콘, 실행 화면 | 지금 그대로 | 스킨별 대체 아이콘은 범위 밖 |

**범위 밖**: 효과음, 스킨별 움직임·Lottie, 스킨별 기리 대사 묶음, 스킨별 글꼴, 스킨별 지도 장소 그림(2026-11-21에 뺐다. 홈 레이아웃이 정해진 뒤 필요하면 새 키로 더한다, 7.3). 스킨이 바꾸는 움직임은 "스킨을 바꿀 때의 0.3초 교차 페이드" 하나다(5.3).

### 1.3 화면별 적용 범위

"스킨"은 그 스킨의 값, "고정"은 모든 스킨이 같은 값이다. 강도 단계의 뜻은 4.1.

| 화면 | 단계 | 바탕 | 무늬 | 강조색이 닿는 곳 | 고정으로 남는 것 |
|---|---|---|---|---|---|
| H 홈 | 강 | `AppBackground` | × 1, 화면에 고정 | 화면의 버튼(시작 버튼, 꾸미기 입구, 메뉴 아이콘)은 앱 공통 버튼 규칙을 따른다. 지도 영역 안에는 쓰지 않는다 | 지도 안의 모든 것(1.2), 말풍선, 기리 |
| H의 칸 카드 시트 | – | `AppBackground` 단색 | 없음 | 시트 안 버튼·아이콘 | 카드, 글자 |
| S 장면 진입 | 중 | `AppBackground` | × 0.5 | 할 차례 번호 원, 주 버튼 | 목록 행 바탕, 완료 체크, 자물쇠, 목표 단어 글자 |
| L1 글자 소개 | 약 | `AppBackgroundQuiet` | 없음 | 진행 막대, 주 버튼, 보조 버튼 | 획 데이터 글자, 번호 원, 단어 카드, **지금 글자(`Ink`)** |
| L2 따라 쓰기 | 약 | `AppBackgroundQuiet` | 없음 | 진행 막대, 주 버튼, 보조 버튼 | 캔버스와 그 안의 모든 선·표시, 판정 줄 |
| W 단어 읽기 | 약 | `AppBackgroundQuiet` | 없음 | 진행 막대, 주 버튼 | 단어 글자, 발음 표기, 단어 그림 |
| QI 퀴즈 안내 | 중 | `AppBackground` | × 0.5 | 주 버튼, 글자 버튼 | 기리, 말풍선 |
| QA·QD 퀴즈 | 약 | `AppBackgroundQuiet` | 없음 | 진행 막대, 주 버튼 | 묻는 글자, 선택지 칸·외곽선, 맞음·틀림 테두리와 아이콘 |
| QC 퀴즈 | 약 | `AppBackgroundQuiet` | 없음 | 진행 막대, 주 버튼, 보조 버튼 | L2와 같음 |
| C1 세션 완료 | 중 | `AppBackground` | × 0.5 | 주 버튼, 글자 버튼 | 체크 배지(`Correct`), 엔 아이콘. 배지 바깥 고리는 그 스킨의 `AppBackground` 단색 3pt |
| C2 장면 완료 | 강 | `AppBackground` | × 1 | 주 버튼, 글자 버튼 | C1과 같음. 열린 스킨 아이템은 스킨 썸네일(5.2)로 |
| K 기리 꾸미기 | 강 | `AppBackground` (미리 보는 스킨의 값) | × 1 | 고른 탭, 쓰는 중 외곽선·체크 배지, 미리 보는 중 점선 | 미리보기 카드 바탕·외곽선, 칸 바탕, 엔 아이콘 |
| I 정보 | 중 | `AppBackground` | × 0.5 | 링크 글자 | 목록 행 바탕, 크레딧 문구 |

- 화면 하나에는 단계 하나다. 같은 화면 안에서 영역마다 단계를 바꾸지 않는다.
- 강·중 화면의 **아래 고정 영역**(주 버튼과 그 위의 기리·말풍선 같은 고정 영역이 있는 화면): 무늬를 빼고 `AppBackground` 단색을 깔고, 위 끝 16pt는 무늬에서 단색으로 이어지는 그라데이션으로 둔다. 말풍선과 버튼 글자 뒤에 무늬가 비치지 않게 하기 위해서다. 홈에서 이 영역이 어디인지는 home-map.md가 정한다.
- 무늬는 화면에 붙어 있고 내용과 함께 스크롤되지 않는다(목록과 지도 모두).

## 2. 토큰 구조

### 2.1 스킨이 채우는 토큰 (9개)

|---|---|---|---|

| `AppBackgroundQuiet` | 색 | 약 화면의 바탕. `AppBackground`를 카드 바탕 쪽으로 옅게 당긴 색 | `#FDF5E6` / `#1F1714` |
| `AccentColor` | 색 | 1.1의 강조 자리 | `#4A2219` / `#F7EEDF` |
| `AccentForeground` | 색 | 강조색 위 글자 | `#FFFDF7` / `#1F1714` |

| `pattern` | 그림 | 무늬 타일 에셋 이름 | 없음 |
| `giriBackdrop` | 그림 | K 미리보기의 기리 뒤 그림 에셋 이름 | 없음 (`CardBackground`로 칠함) |

메타 값: `id`, `itemID`(이 스킨을 여는 리워드 아이템 id, 기본은 null), `nameKo`(검사 출력과 디버그용 이름. 화면에는 쓰지 않는다).

2026-11-18에 `PathFill`을, 2026-11-21에 `mapScenery`·`sceneryScrimDark`를 뺐다(1.2 범위 밖, 4.2).

### 2.2 모든 스킨이 같이 쓰는 고정 토큰 (9개)

`CardBackground`, `Ink`, `InkSecondary`, `Outline`, `Highlight`, `HighlightStrong`, `OnHighlight`, `Correct`, `Wrong`. 값은 visual-rules.md 1.1 그대로다. 안드로이드가 같은 파일을 읽도록 `skins.json`의 `base`에도 적는다(7.2). 대비 증가용 값(visual-rules.md 8.4)도 `base`에 적는다.

### 2.3 라이트·다크와의 관계

- **스킨마다 다크 값을 둔다. 다크 값이 없는 스킨은 넣지 않는다.** 시스템 설정이 다크면 스킨의 다크 값을 쓴다.
- 다크의 바탕은 모두 아주 어둡고 채도가 낮다(상대 휘도 0.029 이하, 2.4). 스킨 사이의 차이는 다크에서 색조, 강조색, 무늬로 남는다. 다크 바탕을 밝게 하면 `Outline`(다크 `#8C7366`)의 3:1이 깨진다.
- 그림(`giriBackdrop`)은 한 벌이다. K의 미리보기 카드 안에만 있어 다크에서도 그대로 둔다(reward-flow.md 8.4).
- 다크의 `AccentForeground`는 그 스킨의 다크 `AppBackground`와 같은 값이다.

### 2.4 접근성과 색 구분 기준

visual-rules.md 1.4의 기준(글자 4.5:1, 글자 아닌 표시 3:1)을 모든 스킨이 지킨다. **무늬가 있는 화면은 바탕 대신 "무늬 선 위의 가장 나쁜 픽셀"로 계산한다**: `바탕 × (1 − 불투명도) + PatternInk × 불투명도`(sRGB 값에서 섞음, SwiftUI·Compose의 기본 합성과 같다).

| 조건 | 라이트 | 다크 | 근거 |
|---|---|---|---|
| 바탕(무늬 섞은 가장 나쁜 픽셀 포함)의 상대 휘도 | 0.72 이상 | 0.029 이하 | 라이트: `InkSecondary`가 4.5:1이 되는 하한. 다크: `Outline`이 3:1이 되는 상한 |
| `CardBackground` / `AppBackgroundQuiet` | 1.07 이상 | 1.16 이상 | 외곽선이 없는 캔버스의 네 변이 기본 스킨보다 덜 보이면 안 된다 |
| `AccentForeground` / `AccentColor` | 4.5 이상 | 4.5 이상 | 주 버튼 글자 |
| `AccentColor` / `AppBackground`, `AppBackgroundQuiet`, `CardBackground` | 3 이상 | 3 이상 | 진행 막대, 번호 원, 쓰는 중 외곽선 |
| `AccentColor` / 보조 버튼 바탕(`AppBackground`에 강조색 15%를 sRGB로 섞은 색) | 4.5 이상 | 4.5 이상 | 보조 버튼 글자 |
| `Ink`, `InkSecondary`, `Correct`, `Wrong`, `HighlightStrong`, `Outline` / 바탕 | visual-rules.md 1.4의 기준 | 같음 | 고정 토큰이 스킨 바탕 위에서도 통과해야 한다 |
| **강조색과 판정색의 거리** (2026-11-21) | `AccentColor`와 `Wrong`, `AccentColor`와 `Correct`: CIELAB ΔE76 **30 이상**. 강조색의 채도 C\*ab가 30 이상이면 CIELAB 색상각 차도 **30° 이상** | 같음 (같은 모드의 값끼리) | 빨강 = 틀림, 초록 = 맞음(visual-rules.md 1.2). 채도가 낮은 강조색(기본 스킨의 진갈색 C\* 23, 크림 C\* 9)은 갈색·무채색으로 읽혀 색상각을 보지 않는다 |
| **강조색과 힌트색의 거리** | `AccentColor`와 `HighlightStrong`, `AccentColor`와 `Highlight`: ΔE76 **20 이상** | 같음 | 노랑·호박 = 힌트 |
| 바탕·무늬의 넓은 면 색상 (HSV) | 125°~160°(채도 25% 이상), 330°~359° 금지 | 같음 | item-art 금지 범위와 같다 |

CIELAB 계산: sRGB → 선형(감마 풀기) → XYZ(D65, sRGB 행렬) → L\*a\*b\*(기준 백색 Xn 0.95047, Yn 1, Zn 1.08883). ΔE76 = √(ΔL\*² + Δa\*² + Δb\*²), 색상각 h = atan2(b\*, a\*), 채도 C\* = √(a\*² + b\*²). 2026-11-17 안의 HSV 색상 금지 범위(강조색 0°~17° 등)는 이 기준으로 바꿨다. HSV 색상각은 어두운 색에서 사람이 보는 색과 어긋나기 때문이다(えき 청록은 HSV로 맞음 초록과 51°지만 CIELAB로는 76°).

**자동 검사**: `tools/check_skin_contrast.py`(새로, developer)가 `skins.json`을 읽어 스킨 × 모드 × (보통 / 대비 증가)마다 위 표를 계산하고, 하나라도 못 넘으면 0이 아닌 값으로 끝난다.

- 표준 라이브러리만 쓴다. 출력은 표(스킨, 모드, 조합, 값, 기준, 결과)이고 결과를 이 문서 3.7에 옮긴다.
- 같은 검사를 Swift 단위 테스트 `SkinContrastTests`로도 둔다. `xcodebuild test`에 묻어 가므로 `skins.json`을 고치고 검사를 잊는 일을 막는다. 파이썬 스크립트는 안드로이드 쪽에서도 같은 결과를 내는 기준이다.
- `PathEdge`는 대비 조건을 두지 않는다. 앞길 선과 잠긴 칸 테는 장식이고 상태는 자물쇠·체크 모양과 길 굵기(6 / 4pt)가 말한다(home-map.md 7.3). 새 팔레트에서는 `PathEdge`가 그 스킨의 `AppBackground`와 눈으로 구분되는지만 본다.

**참배길 주황을 고른 과정** (이슈 #7의 2, 사용자 답 "주황"):

- 색상 자리: 오답 빨강(CIELAB 21° / 20°)과 30° 이상, 힌트 호박(`HighlightStrong` 73°, `Highlight` 82°)과는 ΔE 20 이상이어야 한다. 그 사이의 좁은 띠(CIELAB 약 51°~63°)가 "빨강도 노랑도 아닌 주황"이다. 라이트 58°, 다크 63°로 잡았다.
- 명도: 라이트 강조색은 흰 글자(`AccentForeground`)를 4.5:1로 올리고 보조 버튼의 옅은 바탕 위에서도 글자로 4.5:1이어야 해서 상대 휘도 약 0.10 이하로 어두워야 한다. 그래서 라이트 주황은 밝은 주황이 아니라 **채도가 높은 탄 주황**(HSV 채도 94%)이다. 지난 안의 적갈 `#7A4422`(채도 72%, 휘도 0.08)보다 밝고 선명해 갈색이 아니라 주황으로 읽힌다. 다크는 밝은 주황이다.
- **명도 대비는 기준으로 두지 않는다.** `Wrong`도 같은 글자 대비 조건 때문에 라이트에서 어둡다(휘도 0.12). 둘의 명도 대비는 1.17(라이트), 1.32(다크)로 명도로 가를 수 없다. 둘을 가르는 것은 색상각 37°·43°와 채도이고, 무엇보다 **모양**이다. `Wrong`은 늘 `xmark` 아이콘, 오답 칸의 3pt 테두리, 틀린 획, "정답은 …예요" 문구와 함께 나오고, 강조색은 버튼 바탕·진행 막대·번호 원에만 쓴다. 두 색이 같은 모양에 쓰이는 자리는 없다.
- 두건 빨강 `#E2533F`은 UI에 쓰지 않으므로(visual-rules.md 1.2) 기준에 넣지 않았다. 참고로 주황과 CIELAB 색상각 약 20° 떨어져 있다.

**승강장 청록을 그대로 둔 이유** (이슈 #3, 위임):

- 맞음 초록과 ΔE 43~44, CIELAB 색상각 66~76°로 기준(ΔE 30)을 넉넉히 넘는다. 지난 안이 걱정한 "약 50°"는 HSV 색상각이었다. 어두운 청록은 사람 눈에 파랑 쪽으로 보이고, CIELAB 각이 그것을 보여 준다.
- 노랑-파랑 축(b\*)의 부호가 반대다: 맞음 초록 b\* +21 / +23, 청록 b\* −15 / −11. 적록 색각 이상에서는 빨강-초록 축(a\*)이 약해지고 노랑-파랑 축이 남으므로, 두 색은 색각 이상에서도 파랑과 노랑 쪽으로 갈린다(시뮬레이션은 하지 않았다).
- 옮길 곳이 마땅치 않다. 더 파랑 쪽(200° 이상)으로 옮기면 노렌 쪽빛(HSV 218°)과 두 스킨이 같은 파랑이 된다. 초록 쪽은 금지다.
- 둘이 한 화면에 만나는 곳은 S의 "할 차례 번호 원(청록 `1.circle.fill`)"과 "완료 체크(초록 `checkmark.circle.fill`)"다. 모양(숫자 / 체크)과 설명 줄 문구("할 차례" / "완료")가 다르다. 실기기 확인 목록(9.3)에 남긴다.

### 3.8 남는 약점

1. **のれん과 ゆ의 기리 뒤 그림이 닮았다.** 둘 다 "남색 노렌 + 나무 틀 + 크림 벽"이다. 다시 그리지 않기로 했으므로(이슈 #7의 5) 다음으로 가른다: K에서 칸을 누르면 화면 전체가 그 스킨의 바탕색·무늬·강조색으로 바뀌고(쪽빛 청해파 / 등나무 보라 다테와쿠), 스킨 썸네일 아래 띠(5.2)가 스킨 색을 보여 주며, 칸 이름(のれん / ゆ)이 다르다. 두 그림을 나란히 보는 자리는 K 격자의 썸네일뿐이다.
2. **스킨 4개는 적다.** 장면 8개 가운데 4장면만 스킨을 준다. 가타카나 배경 후보 コンビニ·カフェ·ホテル(reward-system.md 4.6)이 스킨으로 들어오면 7개 + 기본이 된다(9.2).
3. **값이 같다.** 스킨은 앱 전체를 바꾸는데 머리 토핑과 같은 300엔이다. "값은 하나"의 이유(값 표가 생기지 않게)가 여전히 맞아 그대로 둔다(9.2).

### 4.2 H 홈 (강)

- {이름}은 아이템 이름(가나 + 한국어, reward-flow.md 3.8 규칙)이다.
- 미리 보기는 **K 화면 안에서만**이다. 앱 전체 환경값은 저장된 스킨이고, K의 뿌리에만 `.environment(\.skin, previewSkin ?? savedSkin)`을 덮어씌운다. 뒤로 가면 저장된 스킨의 홈이 나온다.
- 확인 창 문구는 그대로다("{가나}({한국어})을/를 {값}엔에 살까요?", "산 아이템은 되돌릴 수 없어요"). 스킨은 언제든 바꿀 수 있으니 되돌릴 수 없는 것은 엔이다.
- 미리보기 카드 아래에 "다른 화면도 이 색으로 바뀌어요" 같은 설명 줄을 더하지 않는다. K 화면 자체가 바뀌는 것으로 충분하고, 세로 계산(reward-flow.md 3.4)을 건드리지 않는다.
- 전환: 바탕·무늬·강조색이 0.3초 교차 페이드(`.easeInOut(duration: 0.3)`). 미리보기 카드 안의 레이어 페이드(0.2초)와 함께 일어난다. "동작 줄이기"면 바로 바뀐다.
- VoiceOver: 슬롯 탭 레이블 "스킨". 미리보기 값의 마지막 항목은 "스킨 {아이템 이름 또는 기본}". 기본 칸은 레이블 "기본 스킨", 값 "쓰는 중" 또는 "기본 스킨으로 바꾸기". 칸을 눌러 안내 줄이 바뀌면 2줄 문구를 알림으로 읽는다.

### 5.4 리워드를 받는 순간

1. **C2에서 열림**: 열린 아이템 줄의 썸네일이 스킨 썸네일이다. 문구와 배치는 그대로. 아직 사지 않았으므로 화면 색은 바뀌지 않는다.
2. **K에서 사기**: 미리 본 스킨이 그대로 확정된다. 산 순간에 따로 바뀌는 것은 점선 → 쓰는 중 외곽선과 체크 배지, 가진 엔 숫자, `.success` 햅틱뿐이다. 산 뒤에 기리가 웃거나 커지는 연출은 없다(visual-rules.md 6.2).
3. 홈에 돌아온 첫 순간의 기리 대사는 이번 범위에 넣지 않는다. 홈의 말풍선 자리가 홈 레이아웃 조사에 묶여 있기 때문이다. 홈 배치가 정해진 뒤 planner(giri-lines.md)와 함께 다시 본다.

### 5.5 "기본 차림으로" 버튼

스킨은 기리의 차림이 아니라 앱의 분위기라서 **"기본 차림으로"는 스킨을 건드리지 않는다**(권장안. 사용자 확인 전, 9.2).

- 버튼은 머리·속재료·밥만 되돌린다. 스킨을 기본으로 돌리려면 스킨 탭의 "기본" 칸을 누른다.
- VoiceOver 힌트: "머리를 요리사 모자로, 밥을 흰 밥으로 바꾸고 속재료를 비워요".
- 버튼의 `disabled` 조건(`isDefaultOutfit`)에서 배경 슬롯을 뺀다. 스킨만 바뀐 상태에서는 버튼이 꺼져 있다.
- 스킨 탭에서 미리 보는 중에 누르면 미리 보기를 끝내고(쓰던 스킨으로 되돌아감) 세 슬롯을 되돌린다.

### 6.2 무늬를 스크립트로 그리는 이유 (이슈 #7의 4)

사용자 답 "더 자연스러운걸로"를 화면에서 더 자연스럽게 보이는 쪽을 고르라는 위임으로 읽고, 아래 세 기준으로 비교했다.

| 기준 | 스크립트 | 이미지 모델 |
|---|---|---|
| 타일 이음매 | 주기 함수와 3×3 이웃 타일로 그려 잘라 내므로 이음매가 수학적으로 없다 | Z-Image는 이어지는 타일을 만들 줄 모른다. 가장자리를 손질해도 선이 끊기거나 굵기가 어긋난다. 무늬는 40pt마다 되풀이되므로 흠 하나가 화면에 30~50번 나타나 격자 모양의 얼룩으로 보인다 |
| 반복 무늬의 균일함 | 청해파·삼잎·다테와쿠는 원래 자로 그린 듯 균일한 기하 무늬다. 균일한 것이 "진짜 무늬"로 보인다 | 원과 육각형의 간격이 조금씩 흔들린다. 6% 불투명도에서는 손그림의 맛은 사라지고 흔들림만 "잘못 그린 것"처럼 남는다 |
| 기리 화풍과의 어울림 | 무늬는 선이 1.25~1.5pt인 옅은 질감이라 기리의 2pt 갈색 외곽선과 겨루지 않는다. 끝과 이음을 둥글게 그려 기리의 둥근 선과 맞춘다. 기리 몸과 밥(`make_onigiri_svg.py`)도 스크립트 그림이라 같은 계열이다 | 스티커 화풍(굵은 외곽선, 평평한 색)은 무늬 타일에 맞지 않는다. 질감이 다른 그림이 화면 전체에 깔린다 |

**결정: 스크립트.** 이것은 CLAUDE.md "그림 생성"(그림 재료는 로컬 이미지 모델로 만든다)의 예외이고, 밥 그림(PLAN.md 3번 "기리 꾸미기")에 이은 두 번째 예외다. 예외의 범위는 "반복 기하 무늬 타일 4장"으로 한정한다. 장면 그림, 소품, 아이템, 지도 그림은 그대로 이미지 모델로 만든다.

### 6.3 무늬 타일 규격

좌표는 pt, 원점은 타일 왼쪽 위, y는 아래로 커진다. 모든 선은 끝과 이음이 둥글다.

| 무늬 | 스킨 | 타일 (pt) | 선 굵기 (pt) | 그리는 법 |
|---|---|---|---|---|
| 청해파 `seigaiha` | noren | 40 × 20 | 1.5 | 원 중심 격자: (40i, 20j)와 (40i + 20, 20j + 10). 위쪽 줄(y가 작은 중심)부터 아래로 차례로, 원마다 ① 반지름 20의 원판을 투명으로 지우고 ② 반지름 19, 14, 9, 4의 동심원 4겹을 그린다. 아래 줄 원이 위 줄 원의 아래 반을 가려 겹친 반원 물결이 된다 |
| 점자 블록 `tenji` | eki | 16 × 16 | 채움 | 지름 4pt 점 하나, 중심 (8, 8). 정사각 격자(승강장 경고 블록의 점 배열) |
| 삼잎 `asanoha` | torii | 30 × 52 | 1.25 | 한 변 30의 정삼각형 격자(밑변 가로). ① 격자의 모든 변(0°, 60°, 120° 세 방향) ② 삼각형마다 세 꼭짓점에서 무게중심까지의 선. 한 주기 높이는 30√3 ≈ 51.96이고 타일은 52로 둔다(세로 0.08% 늘림, @2x 104px, @3x 156px) |
| 다테와쿠 `tatewaku` | yu | 28 × 56 | 1.5 | 가운데(x 14)를 두고 마주 보는 물결선 두 줄. 식은 아래 |

다테와쿠 식(한 타일): 왼쪽 선 `xL(y) = 14 − (6 + 4·cos(2πy / 56))`, 오른쪽 선 `xR(y) = 14 + (6 + 4·cos(2πy / 56))`. y 0에서 두 선은 x 4와 24(가장 벌어짐), y 28에서 x 12와 16(가장 좁음)이다. 이웃 타일과의 간격은 y 0에서 8pt, y 28에서 24pt로 번갈아 부풀고 좁아진다.

- 파일은 색 없는 알파 마스크(흰 선, 투명 바탕) PNG다. 앱이 `PatternInk`로 칠하고 불투명도를 곱한다. 다크용 파일을 따로 두지 않는다.
- 크기: @2x와 @3x 두 벌. 청해파 80×40 / 120×60px, 점자 32×32 / 48×48px, 삼잎 60×104 / 90×156px, 다테와쿠 56×112 / 84×168px.
- iOS: 에셋 `skin-pattern-{name}`(Render As: Template Image). `Image("skin-pattern-seigaiha").renderingMode(.template).resizable(resizingMode: .tile).foregroundStyle(PatternInk).opacity(patternOpacity × 단계 배율)`. 화면 전체(안전 영역 무시)에 깔아 타일 원점이 화면 왼쪽 위에 고정되게 한다.
- 안드로이드: 같은 PNG를 `drawable-xhdpi`·`drawable-xxhdpi`에 `skin_pattern_{name}.png`로. `ImageShader(…, TileMode.Repeated)`에 `ColorFilter.tint(PatternInk)`.
- 이동 중 흔들릴 때 무늬가 지글거리면(모아레) 선을 굵게 하지 말고 불투명도를 낮춘다(9.3).

### 6.4 `tools/make_skin_patterns.py`

- 파이썬 + Pillow(CLAUDE.md의 이미지 도구 규칙). 외부 렌더러 없이 Pillow로 직접 그린다.
- 그리는 순서: 타일 하나의 3×3 이웃 영역을 목표 해상도의 8배로 그림 → 박스 필터로 1/8 축소(타일 경계가 정수 px라 이음매가 생기지 않음) → 가운데 타일을 잘라 냄.
- 출력:
  - `KanaTrip/Assets.xcassets/skin-pattern-{name}.imageset/` (@2x, @3x PNG와 `Contents.json`, template-rendering-intent).
  - `docs/design/skins/patterns-preview.png`: 무늬 4개 × (라이트, 다크) × (강 불투명도, 3배 진하게)를 375×200pt 칸에 깐 확인용 한 장.
  - `--android DIR`을 주면 `DIR/drawable-xhdpi/`, `DIR/drawable-xxhdpi/`에도 쓴다.
- `--check`: 저장소의 PNG가 스크립트 출력과 같은지 비교한다(tools/build_map.py와 같은 방식).
- 시간: 수 초.

### 7.3 읽기 규칙

- 스킨 id는 아이템 id와 같다. 기본은 `default`이고 꼭 첫 번째에 있어야 한다. 저장 상태는 아이템 id만 가지므로(8.2) `itemID`로 스킨을 찾는다.
- 필수 값: `id`, `nameKo`, `colors`의 여섯 키(기본 스킨만 `PatternInk`가 null일 수 있다), 색마다 `light`·`dark`, `patternOpacity`의 `light`·`dark`, `images`의 두 키(값은 null 가능). `pattern`이 null이면 `PatternInk`와 불투명도는 쓰지 않는다.
- `highContrast`가 없는 토큰은 대비 증가에서도 보통 값을 쓴다.
- `schemaVersion`이 앱이 아는 것보다 크거나 스킨 하나라도 필수 값이 빠졌으면 그 스킨을 버리고 기본 스킨으로 그린다(앱이 멈추지 않게). 기본 스킨이 빠졌거나 파일을 못 읽으면 DEBUG에서는 `assertionFailure`, 릴리스에서는 에셋 카탈로그의 Color Set 값(기본 스킨과 같음)으로 그린다.
- 모르는 키는 무시한다. 뒤에 홈 바탕 그림 같은 값을 더할 때는 새 키를 더하고, 없는 앱이 무시해도 화면이 깨지지 않는 값만 더한다. 그렇지 않으면 `schemaVersion`을 올린다.
- 에셋 이름: iOS는 에셋 카탈로그 이름 그대로, 안드로이드는 소문자와 밑줄로 바꾼다(`skin-pattern-seigaiha` → `skin_pattern_seigaiha`, `Item-noren` → `item_noren`).
- 에셋 카탈로그의 `AppBackground`·`AccentColor`·`AccentForeground`·`PathEdge` Color Set은 남긴다(시스템 확인 창 등 환경값이 닿지 않는 곳, 파일을 못 읽을 때). 값이 `skins.json`의 기본 스킨과 같은지 `SkinContrastTests`가 비교한다. 고정 토큰 Color Set도 `base`와 같은지 같은 테스트가 비교한다.

## 8. 데이터와 구현

### 8.1 `rewards.json`의 `background` 슬롯

- 아이템 4개(`noren`, `eki`, `torii`, `yu`)의 id, 이름, 장면, 값은 그대로다. **슬롯 값 `"background"`도 그대로 둔다.** 뜻만 "기리 뒤 장소"에서 "앱 스킨"으로 바뀐다. `"skin"`으로 바꾸면 저장 형식 이행과 안드로이드 이름 맞추기가 생기는데 얻는 것이 없다.
- `_comment`와 `RewardSlot.background`의 주석만 고친다: "앱 스킨. 아이템 id로 skins.json의 스킨을 찾는다. 키가 없으면 기본 스킨."
- 아이템과 스킨의 연결은 `skins.json`의 `itemID` 한 방향이다. `rewards.json`에 색 값을 넣지 않는다.

### 8.2 저장 상태(`RewardState`)

- **이행이 필요 없다.** `equipped["background"]`의 아이템 id가 그대로 "쓰는 스킨"이다. 키가 없으면 기본 스킨. `RewardState.currentVersion`은 그대로.
- 지금 배경을 쓰던 사용자는 업데이트 후 앱 전체가 그 스킨으로 바뀐다. 사용자가 아직 없으므로 안내 화면을 두지 않는다.
- 5.5대로 `RewardRules.resetOutfit`은 배경 키를 남기고, `RewardState.isDefaultOutfit`은 배경 슬롯을 보지 않는다.
- 읽는 쪽: `SkinStore`가 `RewardState`를 보고 지금 스킨을 낸다. 아이템 id에 맞는 스킨이 `skins.json`에 없으면 기본 스킨.

### 8.8 구현 메모 (2026-11-21, developer)

설계 규칙은 고치지 않았다. 구현하면서 설계와 맞지 않거나 설계에 없던 값을 정한 곳만 적는다. 1은 설계 확인이 필요하다.

1. **`CardBackground` / `AppBackgroundQuiet` 기준을 못 넘는 설계 값 (확인 필요).** 2.4 표의 기준(라이트 1.07, 다크 1.16)을 그대로 검사하면 세 조합이 못 넘는다. ① 기본 스킨 라이트 1.065: 기준 1.07이 기본 스킨 값을 올림한 값이라 기본 스킨 자신이 못 넘는다. ② えき 다크 `#191C1A` 1.137, ③ のれん 다크 `#1A191C` 1.158: 둘 다 기본 스킨 다크(1.167)보다 낮아 "기본 스킨보다 덜 보이면 안 된다"(2.4)는 뜻에도 어긋난다(4.4의 "모든 스킨에서 같거나 더 잘 보인다"는 다크에서는 맞지 않는다). 값은 7.2 그대로 두고, 검사 스크립트와 테스트에 **알려진 예외**로 넣어 결과에 "예외"로 찍었다(`KNOWN_EXCEPTIONS`, `Rule.knownExceptions`). 예외가 아닌 실패가 생기면 검사가 실패하고, 예외로 둔 조합이 기준을 넘게 되면 테스트가 예외 목록을 지우라고 알린다. 참고 값: えき 다크 Quiet를 `#171A18`로 하면 1.160, `#161917`이면 1.172. のれん 다크는 `#19181B`이면 1.170.
2. **기본 스킨은 에셋 카탈로그 Color Set으로 칠한다.** 값은 같지만(`SkinContrastTests`가 비교) sRGB 성분으로 만든 Color를 툴바 안(홈 메뉴 아이콘)에 쓰면 합성 결과가 1~10 단위 달랐다. 8.4의 3 "기본 스킨 픽셀이 같음"을 지키려고 기본 스킨은 `Color("AccentColor")` 등 에셋 이름으로 칠한다(`Skin.paint`). 홈 메뉴 아이콘과 앱 루트 `tint`는 사용자 ShapeStyle 대신 `Color`를 준다.
3. **홈 지도 바탕 층.** 4.2대로 `MapStyle.swift`의 스킨 줄만 고쳤지만, 지도 뒤를 단색으로 칠하던 `MapView`의 `.background(MapPalette.ground)` 한 줄은 무늬를 가려 `.background(MapPalette.groundLayer)`로 바꿨다(색 토큰 교체 한 줄, 배치는 그대로). `MapDock`의 꾸미기 입구 `Color.accent` 2곳도 8.3 표대로 `SkinColor.accent`로 바꿨다. 지도 안 다른 요소는 손대지 않았다. 홈은 K의 미리 보기와 상관없이 저장된 스킨이라 `MapPalette`는 환경값 대신 `SkinStore.shared`를 읽는다.
4. **K의 저장된 스킨.** K 화면은 미리 보는 스킨이 없을 때 환경값 대신 `SkinStore.shared.current`를 바로 읽는다. 사기(미리 보기 끝 + 저장)를 한 번에 할 때 0.3초 페이드 중간 화면에 두 스킨과 다른 진한 파랑이 한 번 찍혔다. 루트 환경값이 한 박자 늦게 오는 것으로 보고 이렇게 바꿨고, 바꾼 뒤 사기를 다시 해 끝 화면은 맞는 것을 봤지만 페이드 중간 프레임은 다시 찍지 못했다.
5. **시스템 확인 창 색.** 1.2는 확인 창 버튼을 기본 스킨 값으로 둔다고 했지만, iOS 26에서 칸에 붙인 확인 창(팝오버)의 버튼 글자는 K의 `tint`(미리 보는 스킨의 강조색)를 따랐다. 억지로 맞추지 않는다는 1.2의 방침대로 그대로 두었다.
6. **무늬 층 구현.** `Image(...).resizable(resizingMode: .tile)`에 `PatternInk`를 칠하고 `patternOpacity × 단계 배율`을 곱한다. 스킨 썸네일 띠의 타일 × 0.5는 `scaleEffect`로 줄인다. 대비 증가면 무늬를 그리지 않고 강·중 화면 바탕을 `AppBackgroundQuiet`로 둔다(2.5).
7. **아래 고정 영역.** `.skinFixedBottom()`이 무늬가 보이는 화면에서만 단색 + 위 16pt 그라데이션을 깐다(S의 기리 줄·주 버튼, C1·C2 버튼, QI 아래 버튼). 무늬가 없는 화면(기본 스킨, 약 단계, 대비 증가)에서는 아무것도 그리지 않아 기본 스킨 모습이 바뀌지 않는다. 홈은 지도 코드의 기존 아래 그라데이션·바탕을 그대로 쓴다.
8. **권장안 한곳.** 9.2의 권장안 가운데 코드로 고를 것은 `SkinPolicy`(`KanaTrip/Skin/SkinModel.swift`)에 모았다: "기본 차림으로"가 스킨을 건드리지 않음(`resetOutfitKeepsSkin`), 학습·퀴즈 화면 강도(`learningLevel`), 저장 슬롯(`slot`). 스킨 수는 `skins.json`, 값 300엔은 `rewards.json`, 스킨별 앱 아이콘은 코드가 없다.
9. **`-skinDebug <id>`.** 메모리 진도 실행(`-mapDebugCompleted N`)과 함께 쓰면 그 스킨 아이템을 메모리 상태에서 가진 채 입혀 K에서 "쓰는 중"으로 보인다. 단독으로 쓰면 저장 상태를 건드리지 않고 화면에만 쓴다.
